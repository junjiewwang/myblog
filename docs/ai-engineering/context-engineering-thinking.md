# AI Agent 上下文工程：跨会话记忆共享的挑战与方案

> 💡 **起源**：在使用 AI Coding Agent 过程中的一个思考 — 当前窗口的对话上下文如何在新窗口/新项目中延续？
>
> **日期**：2026-05-26 | **状态**：思考中，待深入研究

---

## 一、问题定义

在使用 AI Agent（如 CodeBuddy、Cursor、Claude Code）时，存在以下矛盾：

1. **当前窗口**：Agent 积累了丰富的上下文（项目结构、设计决策、用户偏好、工具调用历史）
2. **新窗口/新项目**：一切归零，需要重新建立上下文
3. **盲目共享**：如果把所有历史上下文都注入，会导致窗口膨胀、超限、无关信息噪声

### 核心矛盾三角

```
         上下文完整性（什么都想记住）
              ▲
             / \
            /   \
           /     \
          /       \
  窗口限制 ◄────────► 检索相关性
  (128K-200K)          (召回 vs 精确)
```

- **完整性 vs 窗口限制**：信息太多放不下
- **窗口限制 vs 检索**：检索注入可能超限或截断
- **检索 vs 完整性**：检索不准导致关键信息丢失

## 二、业界方案分层

### Level 1：Memory + 按需检索（当前主流）

**代表：** OpenAI Memory、Claude Memory、Cursor

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  短期记忆     │     │  中期记忆     │     │  长期记忆     │
│ (当前会话)    │     │ (会话总结)    │     │ (Memory DB)  │
│              │     │              │     │              │
│ - 完整对话   │     │ - 压缩摘要   │     │ - 结构化KV   │
│ - Tool结果   │     │ - 关键决策   │     │ - 向量索引   │
│ - 文件缓存   │     │ - TODO状态   │     │ - 用户偏好   │
└──────────────┘     └──────────────┘     └──────────────┘
     ↑ 完整                ↑ 有损                ↑ 稀疏
     窗口内直接可用         触发式加载             语义检索注入
```

**特点：**
- Memory 是"显式记忆"，需要触发才存储
- 跨会话时只有 Memory 条目被注入，中间过程丢失
- 适合偏好、原则等不变信息，不适合动态项目状态

---

### Level 2：分层上下文压缩（Context Hierarchy）

**代表：** Claude Code 的 `cb_summary`、Devin

```
┌─────────────────────────────────────────┐
│            上下文预算分配                  │
├─────────────────────────────────────────┤
│  System Prompt         ~5-10K tokens    │
│  Memory/Rules          ~2-5K tokens     │
│  ★ 压缩总结 (summary)  ~3-8K tokens     │  ← 关键层
│  Recent messages       ~50-100K tokens  │
│  Tool results          ~20-50K tokens   │
│  Reserved for response ~10-20K tokens   │
└─────────────────────────────────────────┘
```

**核心思路：** 用"信息密度"换"信息广度"
- 远的信息 → 高压缩比总结（1:10 ~ 1:50）
- 近的信息 → 完整保留
- 关键决策 → 无论远近都保留原文

**问题：** 压缩必然有损，如何判断什么是"关键"？

---

### Level 3：知识图谱 + 结构化存储（Context Graph）

**代表：** Devin、Cognition Labs、mem0

```
                    ┌─────────────┐
                    │  知识图谱    │
                    │  (Neo4j等)  │
                    └──────┬──────┘
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
   ┌────▼────┐       ┌────▼────┐       ┌────▼────┐
   │ 项目A   │       │ 项目B   │       │ 用户偏好 │
   │         │       │         │       │         │
   │ - 架构  │       │ - 架构  │       │ - 代码风格│
   │ - 决策  │       │ - 决策  │       │ - 工具链 │
   │ - 文件  │       │ - 文件  │       │ - 习惯   │
   └─────────┘       └─────────┘       └─────────┘
```

**关键技术：**
- **实体提取**：从对话中自动提取 (主体, 关系, 客体) 三元组
- **图检索**：根据当前意图，沿图谱检索相关节点（比向量检索更精确）
- **项目隔离**：不同项目/空间的记忆天然隔离，避免交叉污染

**优势：** 解决"跨项目上下文隔离 + 相关性"
**劣势：** 图谱构建质量依赖 LLM 抽取能力，维护成本高

---

### Level 4：自主上下文管理（MemGPT / Letta）

**代表：** MemGPT/Letta、AutoGen with memory

```
┌─────────────────────────────────────────────────┐
│                  OS-style Memory                  │
├──────────────┬──────────────┬───────────────────┤
│   Main Ctx   │   Recall     │   Archival        │
│   (RAM)      │   (Cache)    │   (Disk)          │
│              │              │                   │
│  当前窗口    │  近期对话    │  全量历史         │
│  ~128K       │  向量检索    │  向量+全文检索    │
├──────────────┴──────────────┴───────────────────┤
│          Memory Management Agent                 │
│  - 自主决定换入/换出（page in/out）              │
│  - 自主决定压缩/保留                              │
│  - 自主决定检索策略                               │
└─────────────────────────────────────────────────┘
```

**核心思想：** 把上下文管理本身交给 Agent（类比操作系统的虚拟内存）
- **Main Context** = RAM：有限窗口，放最相关的
- **Recall Storage** = Cache：向量化的近期记忆
- **Archival Storage** = Disk：全量持久化存储
- **Memory Agent** = OS Kernel：自主调度换入/换出

**关键问题：** Agent 管理自己的记忆 → 元认知能力要求高

---

### Level 5：Agentic RAG + 多路检索

**代表：** Microsoft JARVIS、Google Gemini Deep Research

```
用户问题 → Query Planning Agent → 多轮检索 → 信息融合 → 回答
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
   向量检索      图检索      SQL查询
   (语义匹配)  (关系推理)  (精确过滤)
        │           │           │
        └───────────┼───────────┘
                    ↓
            Reranker + 预算裁剪
            (按相关性排序，截断到预算内)
```

**关键创新：**
- **Query Decomposition**：把一个问题分解为多个子查询
- **Adaptive Retrieval**：根据窗口剩余预算动态调整检索数量
- **Reranking**：Cross-encoder 重排序，保证在有限预算内最大化信息价值

## 三、核心挑战清单

| 挑战 | 描述 | 难度 |
|------|------|------|
| **什么时候存？** | 对话中哪些信息值得持久化？ | ⭐⭐⭐ |
| **存什么粒度？** | 原文？摘要？三元组？ | ⭐⭐⭐⭐ |
| **什么时候取？** | 新会话开始时？每轮对话前？ | ⭐⭐ |
| **取多少？** | 检索 Top-K 如何适配剩余窗口？ | ⭐⭐⭐ |
| **取得准不准？** | 语义检索 vs 关键词 vs 图遍历 | ⭐⭐⭐⭐⭐ |
| **如何遗忘？** | 过时信息如何失效？矛盾信息如何覆盖？ | ⭐⭐⭐⭐ |
| **跨项目隔离** | 项目A的记忆不应污染项目B | ⭐⭐⭐ |
| **隐私安全** | 敏感信息不应被检索到其他场景 | ⭐⭐⭐⭐ |

## 五、我的实践（当前方案）

在日常使用 AI Agent 编程中，我已经形成了一套"手动版分层上下文系统"：

| 层 | 实现方式 | 作用 |
|----|---------|------|
| L1 长期偏好 | Agent Memory 条目 | 编码原则、设计偏好（跨会话自动注入） |
| L2 项目记录 | `docs/xxx.md` 文档 | 需求分析、实施进展、决策记录 |
| L3 团队共享 | iWiki 文档 | 归档报告、验证结果、可汇报材料 |
| L4 任务追踪 | TAPD 需求单 | 结构化的任务状态和描述 |
| L5 代码关联 | MR 描述 + commit message | 代码变更的上下文 |

**换窗口时**：指向文档 `@docs/xxx.md`，Agent 读取后恢复上下文。
