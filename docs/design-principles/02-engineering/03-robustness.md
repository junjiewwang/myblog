# 健壮性：代码要会「体面地失败」

> 一句话：**健壮性不是「永不失败」，而是「失败时体面、可恢复、不扩散」。**
> 好的系统允许失败，但失败必须可控、可定位、可自愈。

---

## 从可扩展性说起

上一篇留了个尾巴：扩展点开好了，新插入的实现——比如一个新协议 parser、一个新采样策略——**如果它执行失败了，怎么办？**

答案是：这已经超出了「结构设计」的范畴，进入「健壮性」的地盘。健壮性关心的，恰恰是六原则和可扩展性都**没覆盖**的那一半问题：**代码在异常、超时、并发、残留等非理想条件下，还能不能体面地工作。**

---

## 两种哲学：防御式 vs 契约式

先厘清一个理念分歧：

| 哲学 | 立场 | 适用 |
|------|------|------|
| **防御式编程** | 不信任任何输入，处处校验、处处兜底 | 边界入口（HTTP 接口、文件解析、外部数据） |
| **契约式编程** | 明确前置/后置条件，违反即 fail-fast | 模块内部（调用方有义务满足契约） |

**正确姿势是分层**：对外（不可信边界）用防御式，对内（可信模块）用契约式。对外接口上「什么垃圾都要接得住」，对内则「不符合契约就立即报错」，而不是默默吞掉。

## 健壮性的四个支柱（你的 Arthas 案例就是范本）

这四条不是空谈，你博客里的 [Arthas 生命周期管理](/observability/arthas/otel-arthas-lifecycle-management.md) 把它们全部落实了（`【实测】`）：

| 支柱 | 含义 | Arthas 案例里的真实实现 |
|------|------|------------------------|
| **幂等** | 重复执行不会造成重复副作用 | `runningTasks.add(taskId)` 防重复执行 |
| **超时** | 等待/执行有明确上限，不无限挂起 | `effectiveTimeout` + 超时控制 |
| **自愈** | 异常状态能自动清理并恢复 | `cleanupUnhealthyArthasIfNeeded()` 清理残留 |
| **失败定位** | 失败能定位到阶段与根因 | 结构化错误码 + 阶段上报 |

## 正反对比（Go）

**反例**：一次失败就留下「半启动」的残留，下次再也起不来：

```go
func (a *Attacher) Attach(pid int) error {
    if err := a.startArthas(pid); err != nil {
        return err // 直接返回：进程启动到一半，残留下来了，没人清理
    }
    // 无超时地死等就绪
    for !a.isReady(pid) {
        time.Sleep(time.Second) // 如果永远不就绪，这里就永远挂住
    }
    return nil
}
```

问题：① 失败不清理 → 残留；② 无超时 → 可能永久挂起；③ 重复调用 → 可能重复启动。**三种坏味道，就是三条健壮性漏洞。**

**正例**：幂等 + 超时 + 自愈 + 终态：

```go
func (a *Attacher) Attach(taskID string, pid int) error {
    // ① 幂等：同一任务不重复执行
    if !a.runningTasks.add(taskID) {
        return ErrTaskAlreadyRunning
    }
    defer a.runningTasks.remove(taskID)

    // ② 自愈：先清理上一次可能残留的不健康 Arthas
    a.cleanupUnhealthyArthasIfNeeded(pid)

    // ③ 超时：带明确上限地等待就绪
    ready, err := a.awaitReady(pid, a.effectiveTimeout)
    if err != nil {
        a.cleanup(pid) // 失败也清理，不留残留
        return err
    }
    _ = ready
    return nil
}
```

<details>
<summary>💭 想一想：为什么「失败也要清理」这件事，比「成功路径」还重要？</summary>

**答案**：因为「成功路径」通常只执行一次，而「失败路径」在异常、重试、并发下会被反复触发。残留不清理，第一次失败留下的「半截状态」会污染后续所有重试——系统会从「失败一次」恶化为「永远失败」。**健壮性的一半，是在管好失败路径本身。**

</details>

## 健壮性清单：写代码时问自己五句

1. **幂等吗**？同一请求/任务重复进来，会不会造成双份写入、重复副作用？
2. **有超时吗**？每个「等待」和「远程调用」都有上限，不会无限挂起？
3. **能自愈吗**？异常状态（残留、半初始化、断连）能自动检测并恢复？
4. **能定位吗**？失败时抛出的信息，能让我知道「哪个阶段、什么原因」？
5. **有兜底吗**？最坏情况下，是优雅降级，还是 panic 崩溃？

这五句，恰好对应你 Arthas 案例里的五件事：幂等执行、超时控制、自愈清理、结构化错误、状态收敛。

---

## 红线：别把「防御」写成「过度防御」

1. **不要「吞掉一切错误」**。`_ = err` 是健壮性的反面——它把「失败」变成了「不可知的错误状态」。健壮是「体面地失败」，不是「假装没失败」。
2. **内部模块别过度防御**。可信边界内，该 fail-fast 就 fail-fast，层层判空只会掩盖真正的 bug。
3. **降级要有「可恢复」的出口**。熔断、降级之后，要能自动恢复，否则就是「永久降级」。

---

## 小结

- 健壮性 = 失败时可恢复、可定位、不扩散；
- 四支柱：幂等 / 超时 / 自愈 / 失败定位，你的 Arthas 生命周期管理是完整范本；
- 对外防御、对内契约、失败路径要当成功路径一样认真管；
- 但健壮性不能靠「感觉」保证——**你得能验证它。怎么验证？**
