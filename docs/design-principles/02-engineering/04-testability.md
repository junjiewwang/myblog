# 可测试性：好代码是「天生可测」的

> 一句话：**可测试性，是前面所有原则的「验收标准」。**
> 如果一段代码测不了，那它大概率也违反了前面的某条原则。

---

## 从健壮性说起

上一篇说健壮性要靠「幂等、超时、自愈、定位」。但你凭什么相信这些真的生效？——**靠测试。**

于是问题变成：为什么有些代码「测得了」，有些代码「测不了」？答案往往不在测试技巧，而在**代码本身的可测试性**。而可测试性，恰恰是六原则、高内聚低耦合、可扩展性的「副产品」：

> **遵循了原则的代码，天然好测；测不了的代码，多半是原则没做到位。**

---

## 可测试性的五个维度

一段代码好不好测，可以从五个维度看（`【业界通用】` 可测试性经典模型）：

| 维度 | 问的问题 | 测不了的表现 |
|------|----------|-------------|
| **可控性** | 我能控制它的输入吗？ | 输入来自硬编码、全局变量、真实网络 |
| **可观察性** | 我能看到它的输出吗？ | 只写日志、只改全局状态、无返回值 |
| **隔离性** | 我能隔离它的依赖吗？ | 依赖 `new` 在方法内部，无法替换 |
| **可重复性** | 多次运行结果一致吗？ | 依赖时间、随机数、真实数据库 |
| **简单性** | 逻辑足够简单吗？ | 一个函数几百行、几十个分支 |

五个维度里，**「隔离性」** 是工程上最常卡住的一关，也是可测试性的核心——它直指「依赖怎么被注入」。

---

## 核心手段：依赖注入，让「测不了」变「测得爽」

**反例**：依赖硬编码在方法里，测试必须连真实环境：

```go
func QueryCPUUsage(host string) ([]Sample, error) {
    // 硬编码：测试时真的要去连 localhost:8428 的 VictoriaMetrics
    vm := victoriametrics.NewClient("http://localhost:8428")
    return vm.QueryRange(Query{Metric: "cpu_usage", Label: "host=" + host})
}
```

这段代码的「不可测」体现在：你没法在单测里给它一个「假存储」，只能真的起一个 VM。**可控性、隔离性、可重复性全丢了。**

**正例**：依赖通过构造器注入接口，测试注入 fake：

```go
type CPUQuery struct {
    engine QueryEngine // 依赖抽象，可替换
}

func NewCPUQuery(engine QueryEngine) *CPUQuery { return &CPUQuery{engine: engine} }

func (c *CPUQuery) Query(host string) ([]Sample, error) {
    return c.engine.QueryRange(Query{Metric: "cpu_usage", Label: "host=" + host})
}
```

测试时注入一个「假引擎」，不连真实存储：

```go
func TestCPUQuery(t *testing.T) {
    fake := &FakeEngine{ // 实现 QueryEngine，返回预设数据
        samples: []Sample{{Value: 0.42}},
    }
    q := NewCPUQuery(fake)
    got, _ := q.Query("web-1")
    // 断言 got 符合预期
}
```

对比一下就能发现：**让代码「可测」的那一步，就是让它「依赖抽象 + 构造器注入」的那一步——也就是 DIP 篇讲的那一步。**

<details>
<summary>💭 想一想：为什么说「测不了的代码，多半是原则没做到位」？</summary>

**答案**：因为可测试性的五个维度，几乎都能映射回前面的原则——不可控/不可隔离 ↔ 违反 DIP（硬编码依赖）；不可重复 ↔ 逻辑内聚 + 隐藏的全局状态；不简单 ↔ 违反 SRP（一个函数干太多事）。**所以可测试性不是「额外的工程要求」，而是「原则是否落地」的试金石。** 你想写出好代码，先问一句「这能测吗」，往往比背任何原则都管用。

</details>

## Mock 的边界：什么该 mock，什么不该

依赖注入之后，你会面对下一个问题：**该 mock 什么？**

| 该 mock | 不该 mock |
|---------|-----------|
| 外部依赖：网络、数据库、文件系统、时间 | 纯逻辑：纯函数、计算、状态机 |
| 会「变」的依赖：远程服务、第三方 SDK | 稳定的值对象、数据结构 |
| 会让测试变慢/变不稳定的东西 | 被测代码本身的核心逻辑 |

一个朴素的标准：**mock「I/O 边界」，别 mock「业务逻辑」。** 如果一段纯逻辑也要靠 mock 才能测，那说明它和 I/O 耦合得太紧了——这是代码要改的信号，不是测试要加的信号。

比如 [指标冒险之旅](/observability/victoriametrics/metric-journey.md) 里的 `rawRow` 归一化是**纯函数**（输入字节 → 输出 `RawRow`），它**根本不需要 mock**——这是可测试性最好的状态。

---

## 红线：别让「为测试而测试」污染设计

1. **不要为了测试，把不该公开的字段和方法全暴露出去**。用接口 + 依赖注入即可，不必牺牲封装。
2. **别 mock 一切**。mock 越多，测试越脆（和实现细节强绑定），维护成本越高。
3. **可测试性是为「验证正确性」服务的，不是目的**。测试的终极价值是「敢重构」，而不是「覆盖率数字好看」。

## 小结：前两部分串起来

到这里，「道」（六大原则）+「术」（四项工程实践）全部讲完了。它们其实在说同一件事：

> **让变化可控、让失败可控、让验证可控。**

- 六大原则管「变化的方向」；
- 高内聚低耦合管「变化的尺度」；
- 可扩展性管「变化的出口」；
- 健壮性管「失败的体面」；
- 可测试性管「一切是否可验证」。

**但原则始终是抽象的——面对一个具体的「变化场景」，到底该用哪套「成熟招式」去落地？** 这就是设计模式登场的地方。
