# 高内聚与低耦合：代码的「聚」与「散」

> 一句话：**内聚衡量「模块内部有多团结」，耦合衡量「模块之间有多纠缠」。**
> 高内聚低耦合，是六大原则翻译成工程语言后，两个可以「上手量」的指标。

---

## 从「原则」到「指标」

六大原则是方向性的——「要拆类」「要依赖抽象」「别摸内部」。但工程上你需要更落地的尺子：**改完代码，怎么知道自己改得对不对？**

答案是把原则收敛成两个可度量指标：

| 指标 | 度量什么 | 好代码的特征 |
|------|----------|-------------|
| **内聚** | 模块**内部**元素的关联程度 | 一个模块只为**一件事**而存在 |
| **耦合** | 模块**之间**的依赖程度 | 模块之间只通过**最小的接口**交流 |

一句话：**内聚要「高」，耦合要「低」——元素该聚在一起就聚紧，该分开就分干净。**

---

## 内聚：模块内部的「团结度」

内聚有从差到好七级量表，工程上你只需要记住最关键的两头：

| 等级 | 名称 | 特征 | 例子 |
|------|------|------|------|
| 差 | **逻辑内聚** | 因为「逻辑上同类」被塞在一起，实际彼此无关 | 一个 `switch` 里塞所有协议的解析 |
| 中 | 时间内聚 | 因为「同一时刻执行」被放在一起 | 一个 `init()` 里做所有初始化 |
| 好 | **功能内聚** | 模块只为完成**一个**完整功能 | 每个协议一个独立的 parser |

**真实案例**：接入层怎么处理 14 种协议（`【实测】` [指标冒险之旅](/observability/victoriametrics/metric-journey.md)）？

**反例（逻辑内聚）**：

```go
// 所有协议的解析，因为"都叫解析"被塞进一个 switch
func parse(data []byte, protocol string) ([]RawRow, error) {
    switch protocol {
    case "prometheus": // 解析 Prometheus 文本
    case "influx":      // 解析 Influx 行协议
    case "otel":        // 解析 OTLP protobuf
    // ... 每加一个协议，这个函数就再胖一圈
    }
}
```

问题：这些 `case` 除了「都是解析」外，**彼此没有任何关联**——改 Influx 解析，可能碰坏 Prometheus 解析。这是典型的**逻辑内聚**。

**正例（功能内聚）**：

```go
// 每个协议一个 parser，一个模块只为一个功能而存在
type PrometheusParser struct{}
func (p *PrometheusParser) Parse(data []byte) ([]RawRow, error) { /* 只做 Prometheus 解析 */ }

type InfluxParser struct{}
func (p *InfluxParser) Parse(data []byte) ([]RawRow, error) { /* 只做 Influx 解析 */ }
```

每个 parser「只为解析某一种协议」而存在，内部所有代码都服务这一个功能——**功能内聚**。

---

## 耦合：模块之间的「纠缠度」

耦合也有从强到弱的量表，工程上同样记关键几档：

| 等级 | 名称 | 特征 | 例子 |
|------|------|------|------|
| 强 | **内容耦合** | 直接访问另一个模块的**内部数据/字段** | 查询层直接摸 `storage.indexdb` |
| 中 | 控制耦合 | 传一个「控制标志」决定对方行为 | `query(data, mode=1)` |
| 弱 | **数据耦合** | 只通过接口交换**数据** | 通过 `QueryEngine` 接口传查询参数 |

**真实案例**：查询层和存储层怎么打交道（`【业界通用】` 查询/存储分层设计）？

**反例（内容耦合）**：

```go
// 查询层直接操作存储层的内部结构
func (q *QueryService) QueryRange(query Query) ([]Sample, error) {
    q.storage.indexdb.mu.Lock()   // 直接摸存储层的锁
    defer q.storage.indexdb.mu.Unlock()
    q.storage.data.cache.clear()  // 直接清存储层的缓存
    // ...
}
```

这段代码「了解」了存储层内部有 `indexdb`、有 `mu` 锁、有 `cache`。存储层任何内部改动都会炸掉查询层——**内容耦合**，也是上一篇 LoD 警告的「别摸内部零件」。

**正例（数据耦合）**：

```go
// 只通过接口交换数据
type Storage interface {
    QueryRange(q Query) ([]Sample, error)
}

func (q *QueryService) QueryRange(query Query) ([]Sample, error) {
    return q.storage.QueryRange(query) // 只传数据，不碰内部
}
```

查询层只知道「存储层能查」，其他一无所知——**数据耦合**，最弱的一种耦合。

<details>
<summary>💭 想一想：为什么「内容耦合」比「数据耦合」危险？</summary>

**答案**：差别在「**变化的传播半径**」。数据耦合时，存储层内部重构（比如把 `indexdb` 换成别的索引），只要接口 `QueryRange` 不变，查询层无感；而内容耦合时，`indexdb`、`mu`、`cache` 每一个内部零件都是「耦合点」，任何一个变了，查询层都要跟着改。**耦合越强，一处变化波及的范围越大。**

</details>

## 一把可操作的尺子：变化传播半径

判断「聚得对不对、散得对不对」，有个统一口径：

> **改动一处代码，它「波及」的模块数，就是这段代码的质量指标。**

- 内聚低 → 改一个功能要动多个模块（逻辑内聚的 `switch`：加协议要动 `parse` 函数，牵一发动全身）；
- 耦合强 → 改一个模块要改一堆依赖它的模块（内容耦合：改 `indexdb` 要改查询层）。

**高内聚低耦合，本质就是把「变化的传播半径」压到最小。**

---

## 和六大原则的对应关系

这两个指标不是新东西，它们就是六原则的「另一面」：

| 指标 | 由哪些原则驱动 |
|------|----------------|
| **高内聚** | SRP（按变化原因拆类）、功能内聚 |
| **低耦合** | LoD（别摸内部）、DIP（依赖抽象）、ISP（接口拆小） |

所以你会发现：**六原则讲「为什么」，高内聚低耦合讲「量出来是多少」**——两者是一件事的两种说法。

---

## 红线：内聚和耦合是一对要「平衡」的东西

1. **不要为了「绝对低耦合」牺牲「必要的内聚」**。把高度协作、必须一起变的代码硬拆到两个模块，只会多出一堆「中间接口」，耦合没降，复杂度涨了。
2. **内聚的极致是「一个函数干一件事」，但别把简单逻辑也拆碎**。判断标准永远是「变化传播半径」，而不是「函数行数」。
3. **这两个指标是「结果」，不是「目的」**。别为了刷指标而重构，指标是帮你判断「改完是否更好」的镜子。

---

## 小结

- 内聚度量「内部团结」，耦合度量「外部纠缠」；
- 接入层「每协议一 parser」是功能内聚，查询层「只认接口」是数据耦合；
- 统一尺子是「变化传播半径」；
- 现在代码「聚散有度」了，下一个问题是：**怎么让它在面对变化时，能「只插不改」？**
