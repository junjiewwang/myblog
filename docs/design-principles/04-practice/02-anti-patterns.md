# 反模式与过度设计：原则的「副作用」

> 一句话：**原则和模式是药，用错了剂量就是毒。这一篇讲「用过头」长什么样。**
> 学完 6 原则 23 模式，最危险的不是「不会用」，而是「用过头」。

---

## 五种最常见的反模式

### 1. 上帝类（God Object）

一个类什么都干，成为系统的「万能中心」。

```go
// 上帝类：一个 SuperService 包揽一切
type SuperService struct{}

func (s *SuperService) Parse()    {} // 解析
func (s *SuperService) Store()    {} // 存储
func (s *SuperService) Query()    {} // 查询
func (s *SuperService) Alert()    {} // 告警
func (s *SuperService) Report()   {} // 报表
func (s *SuperService) Migrate()  {} // 迁移
```

**危害**：违反 SRP，任何功能变化都改这一个类，回归风险无限放大。
**识别**：一个类的「变化原因」超过 3 个。
**改法**：按变化轴拆（见重构实战篇）。

---

### 2. 面条式代码（Spaghetti Code）

控制流乱缠：深层嵌套、goto 式跳转、无结构的条件。

```go
func process(r *Request) {
    if r != nil {
        if r.User != nil {
            if r.User.VIP {
                for _, item := range r.Items {
                    if item != nil && item.Price > 0 {
                        // 嵌套到第六层，逻辑已经看不清了
                    }
                }
            }
        }
    }
}
```

**危害**：可读性、可测试性、可维护性全面崩坏。
**识别**：条件嵌套超过 3 层、一个函数行数失控。
**改法**：早返回（early return）、抽函数、消除深层嵌套。

---

### 3. 黄金锤子（Golden Hammer）

「手里只有锤子，看什么都像钉子」——学了一个模式，到处套。

```go
// 什么都用工厂：一个空结构体也要工厂方法
type FooFactory struct{}
func (f *FooFactory) CreateFoo() *Foo { return &Foo{} }
// Foo 就一个空结构体，直接 &Foo{} 就完了，非要包一层工厂
```

**危害**：无意义的间接层，代码啰嗦、理解成本高。
**识别**：一个模式的出现，没有对应「变化」的需求。
**改法**：问一句「这里真的有会变的东西吗」，没有就去掉。

---

### 4. 过早抽象（Premature Abstraction）

在**第二处变化还没出现**时，就抽了接口。

```go
// 只有一个实现，就急着抽接口
type Greeter interface {
    Greet() string
}

type EnglishGreeter struct{}
func (e *EnglishGreeter) Greet() string { return "hello" }

// 整个项目里 Greeter 只有 EnglishGreeter 一个实现，接口是纯负担
```

**危害**：抽象方向往往猜错，将来真变化时还得推倒重来。
**识别**：接口只有一个实现、且没有第二个实现的需求。
**改法**：删掉接口直接用具体类型，等第二处变化再抽象（这条和 OCP 篇呼应）。

---

### 5. 为了模式而模式

「这里应该用个策略模式 / 观察者模式」——从模式名字出发，而不是从问题出发。

**危害**：扭曲代码去迁就模式，制造不必要的复杂度。
**识别**：你在「找机会用某个模式」，而不是「解决问题时自然走到某个模式」。
**改法**：回到总纲的「三步法」——先识别变化，再匹配原则，最后才落模式。

---

## 「何时该停下来」判断表

重构/设计时，拿这张表自检，避免过度设计：

| 自检问题 | 停下来的信号 |
|----------|-------------|
| 这个抽象有几个实现？ | 只有 1 个，且看不到第 2 个 → 别抽象 |
| 这里未来真的会变吗？ | 「可能变」≠「会变」→ 别为想象买单 |
| 加了这个模式，复杂度降了吗？ | 没降、反而多了间接层 → 去掉 |
| 能用更简单的方式吗？ | `if-else` 就够 → 别上模式 |

<details>
<summary>💭 想一想：过度设计 vs 设计不足，哪个更常见？</summary>

**答案**：在「刚学完设计模式」的阶段，**过度设计**远更常见。因为设计不足是「不会」，过度设计是「会用但停不下来」——而后者更难察觉（它看起来「很专业」）。判断的黄金标准永远只有一条：**这段代码面对「真实的变化」时，改起来是不是更省力了？** 如果不是，那不管它用了多少模式，都是过度设计。

</details>

---

## 小结

- 原则和模式是工具，不是信仰；
- 上帝类、面条代码是「设计不足」，黄金锤子、过早抽象、为模式而模式是「设计过度」；
- 判断标准始终是「变化的传播半径」和「真实变化时的改造成本」。
