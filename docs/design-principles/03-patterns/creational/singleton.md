# 单例模式：全局唯一，但要「警惕地」用

> 一句话：**保证一个类只有一个实例，并提供全局访问点。**
> 但它是 23 个模式里**最容易被滥用**的一个，请带着警惕读这篇。

---

## 它解决什么尴尬

有些资源**全局只能有一份**：指标注册表、数据库连接池、全局配置。如果到处 `new`，就会出现多份实例、状态不一致。

单例保证「只此一份」，并发安全地提供全局访问。

---

## APM 落点：指标注册表 / 连接池

APM 里的「指标注册表」（所有指标的唯一登记处）、「连接池」（复用网络连接）都是天然的单例（`【业界通用】` 常见设计）。

---

## Go 代码

Go 里用 `sync.Once` 实现并发安全的单例：

```go
// 全局唯一的指标注册表
type MetricRegistry struct {
    mu      sync.RWMutex
    metrics map[string]Metric
}

var (
    registryOnce sync.Once
    registry     *MetricRegistry
)

// GetRegistry：全局唯一访问点，并发安全
func GetRegistry() *MetricRegistry {
    registryOnce.Do(func() {
        registry = &MetricRegistry{metrics: make(map[string]Metric)}
    })
    return registry
}
```

```go
// 使用方：无论在哪调用，拿到的都是同一个实例
r1 := GetRegistry()
r2 := GetRegistry()
// r1 == r2，且并发安全
```

`sync.Once.Do` 保证初始化函数只执行一次，即使并发调用也安全。

<details>
<summary>💭 想一想：为什么说单例是「最容易被滥用」的模式？</summary>

**答案**：因为它本质是**「全局状态」**，而全局状态有三宗罪：
1. **破坏可测试性**：单例很难 mock，测试之间会互相污染（上一个测试改了全局单例，影响下一个测试）；
2. **隐藏依赖关系**：代码里调 `GetRegistry()`，根本看不出「这个函数依赖了注册表」，依赖图是隐形的；
3. **隐式耦合**：所有用单例的地方，都通过这个全局状态间接耦合在一起。

**单例只在「资源真的全局唯一」时合理**（注册表、连接池、配置），把它当「方便全局传参」用就是灾难。

</details>

---

## 对应原则

- **封装**：唯一实例 + 全局访问点收敛在一处；
- **并发安全**：`sync.Once` 保证只初始化一次。

## 何时别用（红线）

1. **「只是为了方便到处拿」**：这是最经典的误用。应该用**依赖注入**把对象显式传进去，而不是偷偷 `GetXxx()`。
2. **需要 mock/替换**：单例几乎不可替换，凡是需要测试隔离的对象，都别做成单例。
3. **「全局配置」也可以用「包级变量 + 注入」替代**：别什么都往单例里塞。
4. **Go 的偏好**：Go 社区通常**宁可用包级变量或依赖注入，也不爱用单例**——因为它破坏了显式的依赖关系。如果你的「单例」可以通过构造器注入传进来，就别用单例。

一句话总结：**能注入就别单例，能传参就别全局。**
