# 分布式 Java Agent 远程控制平面系统

## 项目简介

基于 OpenTelemetry Java SDK 设计并实现 Agent 远程管控扩展，支撑生产环境数千 Java 服务实例的集中式动态配置下发、远程诊断和采样策略热更新，**零重启、零侵入、毫秒级生效**。

---

## 技术亮点

### 1. 通信架构 — Protobuf-only 协议栈 + 双协议统一抽象

- 设计 6 个 Protobuf 定义文件，覆盖指令下发、状态上报、心跳、诊断任务等全链路消息模型，**编解码零反射、包体压缩率 > 60%**
- 抽象 Transport（HTTP/gRPC）+ Operation（PULL/PUSH/HEARTBEAT）两层枚举，上层业务逻辑与底层传输协议完全解耦，**切换协议仅需修改 1 行配置**
- 长轮询 + 即时重连机制：服务端 hold 请求最长 30s，有新指令立即返回，客户端断线后 **指数退避重连（100ms → 5s cap）**，弱网场景下指令到达率 > 99.5%

### 2. 插件化架构 — Facade 门面 + SPI 扩展点

- Facade 门面模式统一协调 10+ 子组件（通信、采样、诊断、增强、健康检查等）的初始化/销毁/异常恢复生命周期，**对外暴露单一入口，降低集成复杂度**
- 基于 Java SPI + AutoConfiguration 实现 `TaskExecutorProvider` 扩展点，新增任务类型（如 ThreadDump、HeapHistogram）**零修改核心代码、零重新打包**
- 插件发现 → 校验 → 注册 → 执行全链路标准化，内置版本兼容性校验，避免 Agent 升级导致插件失效

### 3. 并发设计 — 无锁热切换 + 单线程事件循环

- `AtomicReference<SamplingStrategy>` 实现采样策略无锁热切换，**读路径零开销、写路径 CAS 一次成功率 > 99.9%**（低竞争场景）
- 长轮询通信采用单线程事件循环模型，消除多线程竞态条件，指令串行处理保证时序一致性
- 任务分发器：异步线程池执行 + 可配置超时控制（默认 30s）+ 基于 taskId 的幂等性校验，**重复指令自动去重，任务超时自动回收**

### 4. 动态增强引擎 — 运行时字节码织入/还原

- 基于 ByteBuddy Advice API + `Instrumentation.retransformClasses()` 实现**运行时方法级字节码织入和还原**
- Transformer 生命周期管理：注册 → 激活 → 增强 → 去增强 → 注销，**并发增强上限 50（可配置）**，超限排队等待
- 支持 Bootstrap ClassLoader 注入：通过 `Instrumentation.appendToBootstrapClassLoaderSearch()` 将增强逻辑注入启动类加载器，**覆盖 JDK 核心类增强场景**
- 安全性：增强前快照 + 失败自动回滚 + 类校验，避免字节码损坏导致 JVM crash

### 5. 可靠性保障 — 状态机 + 滑动窗口 + 优雅降级

- **连接状态机（4 态）**：`DISCONNECTED → CONNECTING → CONNECTED → DEGRADED`，明确定义每个状态的转入/转出条件和允许操作
- 滑动窗口健康检查：最近 N 次心跳成功率 < 阈值自动进入 DEGRADED，恢复后自动升级为 CONNECTED
- 策略模式连接准入决策（`ConnectionPolicy`）：根据 Agent 版本、实例负载、网络质量决定是否接受新连接
- **优雅降级**：控制平面不可达时 Agent 自动切换为本地缓存策略运行，业务零感知

## 设计模式（8+ 种）

| 设计模式 | 应用场景 |
|---------|---------|
| **门面 (Facade)** | 统一协调 10+ 子组件生命周期 |
| **策略 (Strategy)** | 连接准入决策、采样策略切换 |
| **状态机 (State)** | 连接状态流转（4 态） |
| **装饰器 (Decorator)** | 采样策略热切换包装器 |

| **模板方法 (Template Method)** | 任务执行器标准化流程 |
| **责任链 (Chain of Responsibility)** | 指令校验 → 路由 → 执行 → 回报 |

## 面试叙述（STAR 法）

### Situation（背景）

> 生产环境数千 Java 服务实例需要动态调整采样率、远程诊断、热更新配置。传统方式需要重启服务或 SSH 登录机器逐台操作，响应慢、风险高、无法规模化。

### Task（任务）

> 设计一套 Agent 远程控制平面，实现：
> 1. 不重启即可热更新配置（采样率、日志级别等）
> 2. 可靠地向海量 Agent 并发下发指令
> 3. 支持运行时远程诊断（线程/内存/方法 Trace）
> 4. 扩展不侵入 OTel SDK 核心，保持社区兼容性

### Action（方案）

> 1. **热更新**：装饰器模式包装采样策略 + AtomicReference 无锁 CAS 切换，读路径零额外开销
> 2. **可靠下发**：长轮询（hold 30s）+ 指数退避重连 + 4 态连接状态机 + 滑动窗口健康检测
> 3. **远程诊断**：ByteBuddy Advice 运行时字节码织入，Transformer 生命周期管理（注册/激活/回滚）
> 4. **零侵入**：Java SPI + AutoConfiguration 自动发现，作为独立 Extension 加载，不修改 SDK 一行代码

### Result（结果）

> - 配置下发 P99 延迟 < 1s，覆盖数千实例
> - Agent 异常自动降级，业务零感知
> - 新增诊断能力只需实现 1 个接口（`TaskExecutorProvider`），开发周期从 1 周缩短至 1 天
> - 成功集成到公司可观测性平台，成为标准基础设施组件

## 面试追问准备

| 追问方向 | 准备要点 |
|---------|---------|
| 为什么不用 WebSocket 而用长轮询？ | 防火墙/代理兼容性更好；无状态重连更简单；服务端无需维护连接池 |
| AtomicReference 的 ABA 问题？ | 采样策略是不可变对象，每次都是新实例 replace，不存在 ABA |
| 字节码增强如何保证安全？ | 增强前 snapshot + retransform 失败自动 rollback + 类校验 + 并发上限 |
| 状态机为什么是 4 态不是 3 态？ | DEGRADED 是半连接态：Agent 本地可用但控制平面指令不执行，区别于完全断开 |
| 如何防止指令风暴？ | 服务端限流 + 客户端指令队列 + 幂等校验去重 |
| SPI 的版本兼容性怎么处理？ | 插件接口携带 `@Since` 版本号，注册时校验 Agent 核心版本是否满足最低要求 |
